# База знаний: Рефакторинг Dead Drop Service (C++ / Crow)

## 1. Архитектура проекта (Clean Architecture)

Мы перешли от монолитного `main.cpp` к многослойной архитектуре ("Clean Architecture"). Это позволяет изолировать бизнес-логику от сетевого кода и упрощает тестирование.

### Структура папок
*   **`cmd/api/`**: Точка входа в приложение (`main.cpp`). Содержит минимум кода, только запуск.
*   **`internal/app/`**: Сборка приложения (`Server`). Инициализирует базу данных (память), хендлеры и запускает веб-сервер.
*   **`internal/domain/`**: Чистая бизнес-логика (`SecretManager`). Ничего не знает о HTTP, JSON или Crow. Работает только с моделями C++.
*   **`internal/delivery/http/`**: HTTP слой.
    *   `handler.h`: Обработчики запросов. Принимают `crow::request`, вызывают доменную логику, возвращают `crow::response`.
    *   `router.h`: Конфигурация маршрутов (Blueprints).
*   **`internal/middleware/`**: Прослойки (логирование, авторизация).

## 2. Проблема `std::bad_alloc` и Crow Blueprints

Самая сложная часть работы была связана с критическим багом фреймворка Crow, из-за которого сервер падал при запуске.

### Симптомы
*   Приложение компилируется успешно.
*   При запуске немедленно падает с ошибкой `std::bad_alloc` или `Segmentation Fault`.
*   Ошибка возникала **только** при использовании `Blueprints` совместно с `Middleware` и разделении кода на разные функции/классы.

### Исследование причин
1.  **Гипотеза 1: Переполнение стека (Stack Overflow).** Crow использует тяжелые шаблоны, что может забивать стек.
    *   *Попытка:* Увеличили стек линкера до 8МБ.
    *   *Результат:* Не помогло.
2.  **Гипотеза 2: Тяжелый объект App.**
    *   *Попытка:* Вынесли `crow::App` в кучу (`std::make_unique`).
    *   *Результат:* Не помогло.
3.  **Гипотеза 3 (Верная): Проблема ссылок в макросах.**
    *   Макросы Crow (например, `CROW_MIDDLEWARES`) используют `decltype(app)`. Когда `app` передается в другую функцию по ссылке (`AppType& app`), внутренняя шаблонная магия Crow ломается при попытке сконструировать middleware стэк, что приводит к некорректной генерации кода и крашу в рантайме.

### Эволюция решений
1.  **Отказ от Blueprints:** Переписали на `CROW_ROUTE(app, ...)`. Работало, но нарушало модульность.
2.  **Inline Setup:** Вернули Blueprints, но код настройки поместили **прямо в `main` (Server::Run)**, где объект `app` создан локально. Это сработало.
3.  **Factory Pattern (Final Code):** Чтобы сохранить чистую архитектуру и работающие Blueprints, мы применили паттерн Фабрика.
    *   `Router` содержит статические методы (например, `GetApiBlueprint`), которые создают, настраивают и **возвращают** объект `crow::Blueprint` по значению.
    *   `Server` получает готовый блюпринт и регистрирует его у себя локально.
    *   *Итог:* Изоляция кода сохранена, баг с памятью побежден.

## 3. Web Development & UI

### Frontend
*   Реализован современный дизайн с использованием CSS переменных и Flexbox.
*   Добавлены поля для **файла** и **TTL** (время жизни), подготовленные для будущего функционала.
*   Реализована логика на чистом JavaScript (`fetch` API) для отправки JSON на сервер.

### Проблема кэширования шаблонов
*   **Проблема:** При изменении `templates/*.html` сервер продолжал отдавать старый дизайн.
*   **Причина:** Сервер запускается из папки `build/`, куда файлы копируются только при первой настройке CMake.
*   **Решение:** Добавлена команда `add_custom_command(POST_BUILD ...)` в `CMakeLists.txt`. Теперь при каждой сборке шаблоны автоматически копируются в папку билда.

## 4. Теория Безопасности (Security)

### Path Traversal / LFI (Local File Inclusion)
Обсуждали риск доступа к файловой системе через URL (например, `GET /secret/../../etc/passwd`).

*   **Теория:** Если сервер слепо подставляет пользовательский ввод из URL в функции открытия файлов (`std::ifstream`), злоумышленник может прочитать любые файлы на сервере.
*   **Наш проект:** Сейчас **безопасен**, так как `SecretManager` хранит данные в оперативной памяти (`std::unordered_map`). Идентификатор `id` используется только как ключ поиска в хеш-таблице, а не как имя файла.
